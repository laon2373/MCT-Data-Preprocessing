SECTION 00

한눈에 보는 전체 흐름

기업의 MCT 원본 로그를 AI가 읽을 수 있는 표 형태로 변환하고, 실제 절삭 구간만 골라 공구별 정상 상태를 만들었다. 실제 고장 라벨이 거의 없어 정상 데이터에 가상 이상 패턴을 주입한 뒤 XGBoost 지도학습을 수행했고, 실제 31일 로그에 다시 적용하여 높은 점수의 원인과 공정 전환 오탐 가능성까지 검증했다.
31개 원본 .log→13줄→1행 파싱→전처리 31열→실제 절삭 219,195행→1분 Window→14 Feature→XGBoost→Anomaly Score→FastAPI+Streamlit
SECTION 01

프로젝트 목표와 현재 수준

목표는 MCT 가공 설비 로그를 분석해 평소와 다른 가공 패턴이 나타나는 시간대를 찾고, 웹에서 업로드·분석·설명할 수 있는 예지보전 프로토타입을 만드는 것이다.

현재 할 수 있는 것

실제 절삭 중인 1분 구간마다 RPM, LOAD, RPM 오차 패턴을 계산하고, XGBoost가 학습한 가상 이상 클래스 쪽으로 얼마나 강하게 판단되는지 점수를 낸다.

가능 높은 점수 시간대 · 공구 · 정상 대비 지표 · 모델 기여 Feature

현재 할 수 없는 것

불가 “몇 시간 뒤 고장”, “고장 확률 99%”, “베어링 고장 확정”, “제품 불량 확률”

실제 고장·정비·OK/NG 라벨이 부족하고 이상 클래스가 합성 데이터이기 때문이다.

SECTION 06

정상 기준: 공구별 Baseline

전체 평균 하나를 쓰지 않았다. 공구마다 원래 사용하는 RPM과 LOAD가 다르기 때문이다. 센서 순간 튐의 영향을 줄이기 위해 평균보다 중앙값을 중심값으로 사용했다.

공구RPM 중앙값LOAD 중앙값
Tool 2약 6,990약 6
Tool 4약 14,989약 11
Tool 13약 22,001약 14
Tool 12약 25,990약 17

Train 기간의 정상 Window만 사용해 공구별 load_center, rpm_std_center, rpmerr_center, rpmerr_tol을 저장했다.

왜 Train만? Validation/Test 정보를 미리 정상 기준에 넣으면 미래 정보를 본 것이 되어 Data Leakage가 생기기 때문이다.
SECTION 07

RPM_ERROR와 1분 Window

RPM_ERROR

RPM_ERROR = SPINDLE_RATE - SPINDLE_RPM

지령 RPM과 실제 RPM 차이다. 정상 절삭의 98% 이상이 ±5 안에 있어 큰 이탈을 보기 좋은 Feature였다.

1분 Window

센서 한 줄이 아니라 약 9~11개의 측정을 묶어 평균·변동·최대 등을 계산했다.

30초는 표본이 적고 5분은 공정 전환이 섞이기 쉬워 1분을 선택했다.

SECTION 08

가상 이상 데이터는 어떻게 만들었나?

실제 고장/정비 라벨이 거의 없어 정상 절삭 데이터를 복사한 뒤 물리적으로 설명 가능한 3가지 이상 패턴을 인위적으로 넣었다.

LOAD_RISE

LOAD가 점점 증가하도록 변형.

RPM_INSTABILITY

실제 RPM 흔들림을 점점 크게 변형.

RPM_ERROR_DRIFT

지령 RPM과 실제 RPM의 차이가 점점 커지게 변형.

실제 절삭 219,195행→10분 Seed 462개→가상 이상 주입→48,240행→1분 Window
중요: 이 이상 데이터는 실제 고장이 아니라 정상 데이터에 가정한 패턴을 넣은 합성 데이터다.

SECTION 10

왜 XGBoost인가? — Trade-off

모델장점현재 단점결정
Random Forest쉬움, 안정적, 정형 데이터트리들이 독립적, 오류를 순차 보완하지 않음Baseline 후보
XGBoost소규모 정형 데이터, 빠름, 비선형, 기여도 설명라벨 필요, 합성 라벨 품질 영향1차 메인
LSTM긴 시계열 학습실제 고장 시계열 부족, 복잡·해석 어려움보류
LSTM Autoencoder라벨 없이 정상 학습공정 전환도 이상 가능, 튜닝 어려움향후
Isolation Forest라벨 없이 가벼운 이상 탐지고장 자체가 아니라 정상 분포 이탈 탐지다음 비교 후보
선택 이유: 최종 데이터가 4,560 Window × 14개 수치 Feature인 소규모 정형 데이터라 데이터 요구량·속도·성능·해석 가능성의 균형이 좋은 XGBoost를 1차로 사용했다.

SECTION 12

Anomaly Score란?

현재 1분 Window가 XGBoost가 학습한 “가상 이상 클래스(1)” 쪽으로 얼마나 강하게 판단됐는지 나타내는 모델 점수.
예시해석
0.003가상 이상 패턴과 매우 다름
0.50모델 기본 이진 분류 경계 근처
0.99학습한 가상 이상 패턴과 매우 유사
금지: “0.99 = 고장 확률 99%.” 실제 고장 라벨을 학습한 모델이 아니기 때문이다.

정상/주의/이상 임계값은 아직 확정하지 않았다.

APPENDIX E

교수님·기업 예상 Q&A

왜 RUN 전체를 안 썼나요?

RUN 안에도 RPM=0 또는 FEED=0인 구간이 있어 실제 절삭만 보려고 RUN & RPM>0 & FEED>0을 사용했습니다.

정상 기준은 평균인가요?

전체 평균이 아니라 공구별 Train 정상 Window의 중앙값을 중심으로 만들었습니다.

이상 데이터는 어디서 났나요?

실제 고장 라벨이 부족해 정상 절삭에 LOAD 증가, RPM 흔들림, RPM_ERROR 증가를 인위적으로 넣어 만들었습니다.

왜 XGBoost인가요?

4,560 Window × 14개 수치 Feature인 소규모 정형 데이터라 속도·성능·해석 가능성의 균형이 좋았습니다.

지도학습인가요?

네. 정상 0 / 가상 이상 1 라벨을 직접 만들어 학습했기 때문입니다.

Anomaly Score 0.99면 고장 확률 99%인가요?

아닙니다. 학습한 가상 이상 클래스와 매우 유사하다는 모델 점수입니다.

비지도학습도 할 수 있나요?

가능합니다. 같은 1분 Window와 14 Feature를 Isolation Forest에 넣어 XGBoost와 실제 로그 결과를 비교할 수 있습니다.

“기업에서 받은 5월 MCT 로그는 한 번의 측정이 13줄로 나뉘어 있어 먼저 한 행으로 파싱했습니다. 전체 481,648행 중 RUN은 약 24만 행이었지만 RUN 안에도 실제 비가공 구간이 있어 RUN이면서 RPM과 FEED가 모두 0보다 큰 219,195행을 실제 절삭으로 사용했습니다. 공구마다 정상 RPM과 LOAD가 달라 Train 정상 데이터로 공구별 중앙값 기반 Baseline을 만들었고, 실제 고장 라벨이 부족해 LOAD 증가, RPM 불안정, RPM 오차 증가의 가상 이상을 만들었습니다. 이를 1분 단위 14 Feature로 만들고 정상 0 / 가상 이상 1로 XGBoost 지도학습을 했습니다.
